# Исправления недостатков высокого приоритета

Изменения относятся к шести пунктам исследовательского отчёта по версии `492430e9`. Целевая среда проверки — ROS Noetic, Python 3 и Linux. Сам отчёт описывает состояние исходной версии.

## Что изменено

1. **UDP-пульт.** Ошибки приёма, короткие и слишком длинные пакеты отбрасываются. Четыре значения декодируются явно как little-endian `int16`. Проверяются диапазоны: `x`, `y`, `r` от −1000 до 1000, `z` от 0 до 1000. Неправильный пакет не публикует команду и не обновляет время последнего управления. Устранены гонка при чтении этого времени и работа отсоединённого потока после уничтожения объекта.
2. **Навигация в текущую точку.** Нулевая и практически нулевая дистанция обрабатываются без деления на ноль. Доля пути ограничена диапазоном от 0 до 1. Проверяется положительная конечная скорость; координаты перед публикацией должны быть конечными.
3. **Повторные запросы.** Флаг занятости защищён объектом с автоматическим освобождением. Повторный запрос с ответом `Busy` не снимает блокировку первого. Та же защита действует для посадки; `release` не вмешивается в выполняющийся запрос.
4. **Потеря TF.** Перед отправкой команды рассчитываются все нужные преобразования. При ошибке или неконечных значениях полётные задания не публикуются; старые координаты и ненулевая скорость не получают новых временных меток. Исключение в таймере записывается в журнал, не завершая узел.
5. **Clover Blocks.** Код исполняется в отдельном процессе с собственной группой процессов. `Stop` отправляет `SIGTERM`, а после ограниченного ожидания — `SIGKILL`. Очистка выполняется при нормальном завершении, исключениях и `SystemExit`; следующий запуск доступен сразу после успешного `Stop`. Обработка ROS-сервисов не зависит от пользовательского цикла. Этот процесс не является песочницей: запускать можно только доверенные программы.
6. **Сетевой доступ.** ROS bridge, видео и UDP-пульт доступны только через loopback. Веб-терминал также привязан к loopback, параметр `--unsecure` удалён, автоматическая активация терминала отключена. В сборку образа добавлена защита динамических TCP-портов ROS для IPv4 и IPv6. При невозможности применить защиту зависимые системные службы ROS не запускаются.

## Проверка на компьютере

После установки зависимостей и обычной сборки Catkin:

```bash
cd ~/catkin_ws
catkin_make
source devel/setup.bash
rostest clover safety.test
catkin_make run_tests
catkin_test_results
(cd build && ctest -R 'clover_safety_test|clover_blocks_lifecycle' --output-on-failure)
```

Тест `safety.test` самостоятельно создаёт ROS-среду с имитацией FCU; настоящий контроллер или квадрокоптер подключать не требуется. Его узлы используют стандартные имена: отдельный ROS master исключает конфликт с работающим дроном.

Проверки без ROS из корня репозитория:

```bash
g++ -std=c++11 clover/test/safety.cpp -o /tmp/clover-safety-test
/tmp/clover-safety-test
python3 -m unittest discover -s clover_blocks/test -v
```

## Установка защиты на существующий образ

Обычный `catkin_make` не устанавливает системный сетевой фильтр. Новый образ получает его через `builder/image-build.sh`. На уже установленном образе Raspberry Pi требуются отдельные действия от администратора:

Сборщик образа повторно получает код из `origin` по идентификатору коммита. Для полной сборки образа исправленный коммит должен быть доступен из указанного удалённого репозитория; локальный Git bundle сам по себе не является таким HTTP-источником. Для проверки из bundle используйте обычную сборку Catkin и установку системных файлов ниже.

```bash
sudo apt-get install iptables
sudo install -m 755 builder/assets/clover-network-guard /usr/local/sbin/clover-network-guard
sudo install -m 644 builder/assets/clover-network-guard.service /etc/systemd/system/
sudo install -m 644 builder/assets/roscore.service builder/assets/clover.service /etc/systemd/system/
sudo install -m 644 builder/assets/butterfly.service builder/assets/butterfly.socket /etc/systemd/system/
sudo systemctl disable --now butterfly.socket butterfly.service
sudo systemctl daemon-reload
sudo systemctl enable --now clover-network-guard.service
sudo systemctl restart roscore.service clover.service
```

Эти команды выполняются из корня репозитория на Raspberry Pi со штатными службами Clover, при остановленном аппарате. Перезапуск ROS прерывает текущие программы. Сетевой фильтр разрешает новые внешние TCP-подключения только к портам 22, 80 и 443, блокирует остальные входящие TCP-порты и UDP 35602; существующие соединения и прочие UDP-службы сохраняются. Поэтому нестандартные внешние сервисы потребуют отдельной административной настройки. Фильтр не меняет правила других цепочек и обновляет собственную цепочку атомарно.

## Веб-интерфейс через SSH

С компьютера оператора выполните, заменив имя пользователя и адрес:

```bash
ssh -N -L 127.0.0.1:8000:127.0.0.1:80 \
  -L 127.0.0.1:9090:127.0.0.1:9090 \
  -L 127.0.0.1:8080:127.0.0.1:8080 pi@192.168.11.1
```

Затем откройте `http://127.0.0.1:8000/clover_blocks/`. Включение Blocks по-прежнему требует `blocks:=true`. Используйте собственные SSH-учётные данные; штатные общие пароли нельзя считать защитой.

Старые мобильные приложения, отправляющие широковещательные UDP-пакеты, больше не управляют аппаратом напрямую. Для удалённого UDP требуется отдельный аутентифицированный туннель или адаптация клиента: обычный `ssh -L` пересылает TCP, а не UDP. Доступ к веб-терминалу следует отдельно включать только при настроенной аутентификации.

## Границы проверки

Проверены компиляция `simple_offboard` и `rc` в отдельной сборке Catkin, регрессионные тесты с реальными ROS-узлами и имитацией FCU, штатные проверки offboard и жизненный цикл дочерних процессов. Полная сборка образа Raspberry Pi, симуляция динамики PX4 и реальные полёты не выполнялись.

При потере TF используется настроенная в PX4 реакция на потерю OFFBOARD: её фактическое действие зависит от версии прошивки и параметров, включая `COM_OF_LOSS_T`. Восстановление TF возобновляет поток заданий, но само по себе не переключает контроллер обратно в OFFBOARD. `Stop` останавливает программу Blocks и не заменяет команду посадки. Испытания полётных последствий должны начинаться с симулятора и проверки конфигурации контроллера.
